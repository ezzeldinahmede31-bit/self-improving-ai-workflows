# Compensatory Router

The pack exists to make strong-model *habits* automatic. At the start of any
substantial task, pick the primary compensator and say it in one line. Then
work. This is the difference between "has skills" and "uses skills".

## Proactive stack (15-skill pipeline — fires automatically)

**STATE -1 — MANDATORY REASONING GATE on EVERY request (user rule: 🧠 التفكير
والاستدلال شغّال مع أي طلب، مش بس المهام المعقدة):** load `frontier-deep-reasoner`
FIRST on any request, no exceptions, and apply its decomposition ladder to the
incoming request BEFORE anything else (before clarify, before omni, before any
task-specific row): Problem → Constraints → Steps → Verify → Output. This is
THE one skill guaranteed on every request, and it always runs first. The rest
of the stack below routes after this gate; the reasoning ladder then rides
along as the reasoning backbone of whatever task row fires.

**STATE -2 — MANDATORY VIDEO-SKILL-PACK BASELINE on EVERY request (user rule:
المهارات ديه تشتغل بشكل أساسي مع أي طلب — no exceptions):** the 5 video skills
fire as a BASELINE layer on every request, composing with the task-specific row
below, not replacing it:
- `using-superpowers` (obra pack orchestrator): before touching the project,
  run the plan→review discipline — `writing-plans`/`executing-plans` structure
  the work, `verification-before-completion` gates delivery, and
  `test-driven-development` guards code changes. For any request whose outcome
  is code/UI, route the production step through `impeccable` (frontend
  architecture + UI quality). For any multi-session or 'my project' work, load
  `remembering-conversations` so the user never re-explains their project.
  `wizard` observes how the user works and evolves skills in the background.
- The task-specific row below still governs the actual HOW; this baseline only
  adds plan-first, verify-before-completion, and quality discipline around it.

**STATE -2b — MANDATORY AUTOMATIC SKILL DISCOVERY on EVERY request (user rule:
find-skills تشتغل أوتوماتيك في الخلفية من غير ما ترجعلي):** while ANY task runs,
`find-skills` resolves the task's domain against the LOCAL LIBRARY first —
scan `memory/skills-library.md` (the generated one-line index of every
installed skill, grouped by this router's registry buckets) for an installed
skill that already covers the task; if found, adopt it directly and stop. Only
when NO installed skill fits does it check the background for a better
off-the-shelf skill (skills.sh / `npx skills find`). If a match with real
traction (install count 1K+, trusted owners) is found, INSTALL it directly into
`.opencode/skills/` (re-check frontmatter), REGISTER it in this router via
`venv/bin/python scripts/router_register.py <name>` (adds a routing row marked
`(Auto-registered)` + a registry entry + bumps the total + auto-refreshes
`memory/skills-library.md`), adopt it for the current task, and report the
install in the final answer. If NO installable match exists, CREATE the skill
in-house: write `.opencode/skills/<slug>/SKILL.md`, run
`venv/bin/python scripts/build_gates_pipeline.py .opencode/skills/<slug>/SKILL.md --no-hitl`
until VERDICT READY_FOR_DEPLOYMENT (exit 0), then `router_register.py <slug>`
(which also adds its library entry). DO NOT pause the task to ask the user for
confirmation and DO NOT come back with 'should I install X?'. Exceptions that
DO stop and ask: paid/high-risk (`Med/High` Socket/Snyk flagged) or huge packs
(>5 skills) — those get a one-line note, not a blocking question.

**STATE -2c — MANDATORY GATE-FIRST-PASS BASELINE before EVERY n8n workflow /
AI agent build (user rule: أي workflow أو agent تبنيه لازم يعدي على البوابات من
أول مرة — build it right the first time):** `gate-first-pass-builder` fires
before any node is placed on ANY build/edit/creation of a workflow, agent,
automation, or n8n JSON. It reads the LIVE avoid-list from the accumulated
rejection history (`venv/bin/python scripts/gate_first_pass_avoidlist.py
--top 10` reading `memory/n8n_error_patterns.json`) so the design is blocked
from the real gate failures (schema cache preflight first, pinned data +
dry-run evidence, Error Trigger / continueOnFail, sub-workflow split for large
graphs, agent wiring: ai_languageModel connected + allowed_tools declared +
maxIterations ceiling + systemMessage, webhook auth when writing, credentials
never inline, integer typeVersion, no orphaned/dangling nodes, RAG
embeddings/store/splitter wiring), then builds incrementally and runs
`build_gates_pipeline.py --schema-cache memory/n8n_schema_cache.json` until
VERDICT READY_FOR_DEPLOYMENT (exit 0). A gate rejection on a rule-compliant
build is reported as a possible false positive — never worked around by
reshaping the workflow. Composes with STATE -2 video baseline, STATE 0 clarify,
and the n8n task rows below (incremental-generation, build-gates-pipeline,
n8n-schema-guardrail, automation-known-issues-compass).

**STATE 0 — MANDATORY discovery loop on ANY request (user rule, applies to
everything):** `clarify-before-execute` FIRST — if the request is not fully
specified, SEARCH first (web/skills.sh/codebase/memory) to ground it, then
COME BACK and ask the user the load-bearing questions (goal, exact
deliverable, audience, constraints, done-when) in ONE compact round with
defaults, get the confirmation contract, and only then proceed to the omni
pipeline below. Never build on silent assumptions; never ask twice about
what search/memory already answers.

**MANDATORY for EVERY request (user rule, applies to everything):** run
`omni-request-orchestrator` FIRST on any task — extract purpose + target
audience → analyze their psychology with LIVE 2025+ web research
(`audience-psychology-analyst` + `web-search`/`deep-research`) → pick the
matching marketing levers (`influence-psychology`/`conversion-psychology`/
`persuasion-principles`/`marketing-psychology`) → hand the psychological
brief to the production skill for THAT task (`video-edit`, `copywriting`,
`social-media`, n8n stack, etc.) → verify output against the psychology.
Psychology is NEVER "unrelated" — even code/n8n tasks get the audience pass.
**If unsure which skills apply (novel/unusual task): fire ALL the relevant
packs together** — psychology + research + quality/security + production —
and synthesize; never leave a skill idle because it "looks unrelated"
(user rule: شغل كل المهارات مع بعض حتى لو شايف إن ملهمش لزمة).
Then continue with the task-specific row below.

For **any system build or refactor**, do NOT start coding from the raw prompt.
Expand first, decompose second, document last. This is the 30% a frontier
model does implicitly:

| Trigger | Skill |
|---|---|

Stacking rules: the add-on skills COMPOSE with the base ones. Example routing
for a large refactor: `long-horizon-executor` (plan/checkpoints) +
`ast-codebase-graph-navigator` (navigate) + `multi-agent-consensus-engine`
(review the plan) + `tdd-sandbox-proof-engine` (verify each step) +
`adversarial-self-falsifier` (attack the final result).

## Activation line (say it, do not skip it)
`[router] primary=..., support=...` — one line, then execute the chosen protocol.

## Anti-patterns (do not do)
- Do not recite several skills "in case" — one primary governs the flow.
- Do not skip the chosen protocol mid-task because it feels slow; the slowness

- Do not apply `long-horizon-executor` to a one-step question.
